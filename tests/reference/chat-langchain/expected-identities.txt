# WHY THIS REPOSITORY. v6.1 §6's Build 1 demo requires "one AI deployment --
# real code, not fixtures". This is a *deployed* agent rather than a framework:
# a support agent with system prompts held as module constants and as a
# top-level `instructions.md`, four `@tool`-decorated functions, three pinned
# vendor models with a declared fallback chain, an MCP server as its document
# source, and one `define_deep_agent` root. Every referent the AI pack claims to
# extract exists here in the shape a client would actually write it -- which a
# framework repository, whose job is to *define* those shapes rather than use
# them, would not have given us.
#
# WHAT THIS FILE IS. Identities an FDE would name from memory after ten minutes
# in this repository. `adopt map --check-expected` asserts every one is present
# and names each miss, exiting 4 on any.
#
# WHY IT IS CURATED RATHER THAN A COVERAGE RATIO. A recall percentage improves
# when its denominator shrinks, and every incentive around one points that way.
# A named list cannot be gamed like that: either `search_support_articles` is in
# the map or it is not, and the failure names it. Removing an entry to make the
# check pass is a visible edit to a reviewed file.
#
# WHAT IS DELIBERATELY ABSENT. Prompts assembled at runtime -- an f-string built
# from fragments, a `ChatPromptTemplate` with variables, a prompt pulled from a
# hub at import -- have no text `adopt map` can read without executing the
# client's code, which it never does. This repository holds its prompts as
# constants, so the boundary does not bite here; it is stated so that a future
# repository where it does bite is a named miss rather than a silent thin map.
